HOW TO READ THIS DOCUMENT
--------------------------
Each agent section is structured as:

  [AGENT NAME]
  ├── BRAIN SPEC       → Model type, fine-tune target, context config
  ├── TOOL STACK       → Every tool, library, API with version/config notes
  ├── INTERFACES       → Inputs accepted / Outputs produced
  └── FUNCTIONAL REQ   → FR-XX.Y.Z task/subtask tree (SHALL language)

"Brain" = the cognitive engine powering the agent's reasoning.
"Tools" = the external systems/libraries the agent is allowed to invoke.

All agents MUST receive Rengoku security clearance before tool invocation.
All agents communicate exclusively via the IPC Bus (HMAC-signed envelopes).

Model Type:     Large Language Model (LLM) — Orchestration-Tuned
Base Model:     GPT-4-class or Claude Opus-class (128k+ context window required)
Fine-Tune:      Supervised fine-tuning on:
                  - Tree-of-Thought (ToT) reasoning traces

Context Config: Full session context retained at Kagaya layer ONLY.

Temperature:    0.2 (low — deterministic orchestration, not creative)
Token Budget:   12,000 tokens per decomposition pass (enforced hard ceiling)
Prompt Cache:   System role prompt + agent registry MUST be cached between turns

Tool 1: DAG Constructor
  Library:    NetworkX (Python) — v3.x
  Purpose:    Build, validate, and traverse directed acyclic execution graphs
  Config:     Topological sort on every DAG build to detect cycles pre-execution
  Interface:  dag.add_node(task_id, agent=, priority=, timeout_ms=, token_budget=)
              dag.add_edge(dependency_task_id, dependent_task_id)
              dag.topological_sort() → ordered execution list
              dag.parallel_levels() → list of independent node batches

Tool 2: State Matrix Evaluator
  Library:    Custom in-process state store (Redis or in-memory dict)
  Purpose:    Real-time tracking of all 9 agent states + active task counts
  Schema:     { agent_id: { state: IDLE|RUNNING|BLOCKED|FAILED|TIMEOUT,
                             current_task_id: str|null,
                             last_heartbeat_ts: int,
                             restart_count: int } }
  Config:     Heartbeat timeout = 5000ms (agent presumed dead if exceeded)
              State transitions logged with timestamps to audit stream

Tool 3: systemctl Wrapper
  Interface:  Python subprocess wrapper around systemctl
  Commands:   start <agent_unit> | stop <agent_unit> | restart <agent_unit>
              status <agent_unit> → returns State Matrix entry
              enable <agent_unit> | disable <agent_unit>
  Config:     Each agent runs as a dedicated systemd unit file
              Unit files define: memory limit, CPU quota, restart policy

Tool 4: Conflict Resolution Matrix
  Type:       In-memory priority table (static config + runtime overrides)
  Schema:     { (agent_A, agent_B, resource): winner_agent_id, strategy }
  Strategies: PREEMPT (kill lower priority), QUEUE (wait), SPLIT (partition)
  Config:     Loaded from conflict_matrix.yaml at startup, hot-reloadable

Tool 5: IPC Bus Client
  Library:    ZeroMQ (PyZMQ) — DEALER/ROUTER pattern for agent-to-agent routing
  Config:     HMAC-SHA256 signing on all outbound messages
              Message schema: { sender_id, target_id, message_type,
                                payload, timestamp, correlation_id,
                                clearance_token, hmac_signature }
  Endpoints:  Each agent binds a named ZMQ socket (ipc:///tmp/hashira/<agent>.sock)

Tool 6: Response Synthesizer
  Type:       LLM call (same Kagaya brain model)
  Purpose:    Final aggregation of sub-agent outputs into user-facing response
  Input:      Structured JSON outputs from all DAG leaf nodes
  Constraint: Single synthesis call per user request — NOT per agent turn

FUNCTIONAL REQUIREMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FR-01.1  Intent Normalization
  └─ FR-01.1.1  Kagaya SHALL receive raw user input and sanitize it for:
                prompt injection patterns, shell escape sequences, null bytes,
                and overlong unicode sequences before any processing.
  └─ FR-01.1.2  Kagaya SHALL normalize all valid input into a canonical
                IntentObject:
                  { intent_id: uuid, type: QUERY|TASK|EVENT|FAILURE,
                    raw_text: str, normalized_text: str,
                    session_id: str, timestamp: int }
  └─ FR-01.1.3  Kagaya SHALL classify intent type using a lightweight
                classifier (rule-based regex + keyword matching) BEFORE
                invoking the LLM, to save tokens on trivial classifications.
  └─ FR-01.1.4  Kagaya SHALL reject and return structured errors for inputs
                that fail sanitization — no LLM call SHALL be made on
                rejected inputs.

FR-01.2  DAG Construction
  └─ FR-01.2.1  Kagaya SHALL invoke its LLM brain with a structured
                decomposition prompt for each valid IntentObject, requesting
                output as a JSON task list with dependency annotations.
  └─ FR-01.2.2  Kagaya SHALL feed the LLM task list into the DAG Constructor
                (NetworkX) to build a validated acyclic execution graph.
  └─ FR-01.2.3  Kagaya SHALL run topological_sort() on every DAG immediately
                after construction. Any detected cycle SHALL cause the
                full DAG to be rejected and the LLM re-prompted with the
                cycle error as feedback (max 2 re-prompt attempts).
  └─ FR-01.2.4  Kagaya SHALL annotate each DAG node with:
                  - target_agent_id (exactly one per node)
                  - priority: CRITICAL | HIGH | NORMAL | LOW
                  - timeout_ms: per-agent default or task-specific override
                  - token_budget: integer token ceiling for LLM agents
                  - rengoku_required: bool (true for all tool-invoking nodes)
  └─ FR-01.2.5  Kagaya SHALL call parallel_levels() and dispatch all nodes
                in the same parallel batch simultaneously, not sequentially.

FR-01.3  Agent Lifecycle Management
  └─ FR-01.3.1  Kagaya SHALL read each agent's last_heartbeat_ts from the
                State Matrix every 5000ms and flag any agent whose last
                heartbeat exceeds the threshold as TIMEOUT.
  └─ FR-01.3.2  Kagaya SHALL issue systemctl restart <unit> for any TIMEOUT
                or FAILED agent, up to restart_count = 3.
  └─ FR-01.3.3  Kagaya SHALL mark an agent DEGRADED after 3 failed restarts
                and reroute its pending tasks to a fallback:
                  - Muichiro fallback → Kagaya direct code gen (reduced quality)
                  - Shinobu fallback → Web search via Kagaya (no local RAG)
                  - Obanai fallback → Temporary in-memory store
                  - All others → User notification via Zenitsu + graceful error
  └─ FR-01.3.4  Kagaya SHALL update the State Matrix atomically on every
                lifecycle event using a mutex lock to prevent race conditions.

FR-01.4  Conflict Resolution
  └─ FR-01.4.1  Kagaya SHALL detect resource contention (two agents requesting
                the same file lock, network port, or GPU slice) by monitoring
                IPC Bus BLOCKED state messages.
  └─ FR-01.4.2  Kagaya SHALL resolve conflicts by consulting the Conflict
                Resolution Matrix (conflict_matrix.yaml) and applying the
                defined strategy (PREEMPT | QUEUE | SPLIT).
  └─ FR-01.4.3  Kagaya SHALL log all conflict events to the audit stream with
                both agent IDs, the contested resource, and resolution outcome.

FR-01.5  Response Aggregation
  └─ FR-01.5.1  Kagaya SHALL collect CompletionReceipt objects from all DAG
                leaf nodes before beginning synthesis.
  └─ FR-01.5.2  Kagaya SHALL invoke the Response Synthesizer (LLM call) ONCE
                passing all leaf outputs as a compact JSON bundle.
  └─ FR-01.5.3  Kagaya SHALL attach an ExecutionSummary to every response:
                  { agents_used: [], total_ms: int, retries: int,
                    token_total: int, failures: [] }
  └─ FR-01.5.4  Kagaya SHALL strip all internal agent IDs, clearance tokens,
                raw tool outputs, and sandbox identifiers from the
                user-facing response unless the user explicitly requested
                debug output.

FR-01.6  Session Token Tracking
  └─ FR-01.6.1  Kagaya SHALL maintain a per-session cumulative token counter
                updated after every LLM call across all agents.
  └─ FR-01.6.2  Kagaya SHALL trigger a Zenitsu WARNING notification when
                session tokens exceed 80% of the configured session ceiling.
  └─ FR-01.6.3  Kagaya SHALL halt LLM calls and return a graceful token-limit
                error when the session ceiling is reached.

FUNCTIONAL REQUIREMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FR-02.1  Directive Validation
  └─ FR-02.1.1  Inosuke SHALL validate every incoming OperationalDirective
                schema before execution, rejecting payloads missing required
                fields: directive_id, type, steps[], rengoku_clearance_token.
  └─ FR-02.1.2  Inosuke SHALL verify the rengoku_clearance_token cryptographic
                signature before processing any step. Invalid tokens SHALL
                cause immediate task rejection and escalation to Kagaya.
  └─ FR-02.1.3  Inosuke SHALL validate each step object for action type
                membership in the allowed action registry:
                  BROWSER: [navigate, click, type, scroll, screenshot,
                             extract, submit, wait, evaluate]
                  PROVISION: [install, remove, configure, start_service,
                               stop_service, clone_repo, apply_template]

FR-02.2  Browser Session Management
  └─ FR-02.2.1  Inosuke SHALL request Rengoku sandbox clearance BEFORE
                launching any browser session, passing the target URL
                and session profile.
  └─ FR-02.2.2  Inosuke SHALL create one isolated Playwright BrowserContext
                per directive, with fresh cookies, local storage, and cache.
  └─ FR-02.2.3  Inosuke SHALL capture a full-page screenshot after every
                browser action step and attach it to the ExecutionLog.
  └─ FR-02.2.4  Inosuke SHALL intercept and log all network requests made
                during browser sessions, forwarding the request log to
                Rengoku for post-session audit.
  └─ FR-02.2.5  Inosuke SHALL destroy the BrowserContext immediately after
                task completion or failure — no session persistence allowed.
  └─ FR-02.2.6  Inosuke SHALL detect CAPTCHA challenges (via page title
                heuristics, DOM class names, or HTTP 403 patterns) and
                classify the step as CAPTCHA_BLOCKED without retrying.

FR-02.3  DOM Interaction Execution
  └─ FR-02.3.1  Inosuke SHALL use page.accessibility.snapshot() to build
                an ARIA element map before each interaction to reduce
                DOM ambiguity failures.
  └─ FR-02.3.2  Inosuke SHALL prefer ARIA roles and data-testid selectors
                over CSS class selectors for element targeting (class names
                change; roles are semantically stable).
  └─ FR-02.3.3  Inosuke SHALL validate element visibility and interactability
                before issuing click or type actions (is_visible + is_enabled).
  └─ FR-02.3.4  Inosuke SHALL inject an explicit wait (waitForNetworkIdle)
                after navigation actions before proceeding to the next step.

FR-02.4  Environment Provisioning Execution
  └─ FR-02.4.1  Inosuke SHALL capture a machine state snapshot via
                Environment Diff Reporter before executing any provisioning
                playbook.
  └─ FR-02.4.2  Inosuke SHALL execute Ansible playbooks with
                ANSIBLE_STDOUT_CALLBACK=json to produce machine-parseable
                output for CompletionReceipt generation.
  └─ FR-02.4.3  Inosuke SHALL run post-provision health checks defined in
                the directive's verify_condition field and mark the step
                FAILED if the health check does not return expected output.
  └─ FR-02.4.4  Inosuke SHALL capture the post-provision machine state and
                produce an EnvironmentDiff JSON attached to the receipt.

FR-02.5  Auto-Recovery Execution
  └─ FR-02.5.1  Inosuke SHALL classify the failure type of each failed step
                BEFORE deciding to retry:
                  TRANSIENT → network timeout, element not ready, HTTP 5xx
                  PERMANENT → HTTP 404, missing required dependency, bad config
                  SECURITY_BLOCK → Rengoku DENY, clearance token invalid
  └─ FR-02.5.2  Inosuke SHALL retry only TRANSIENT failures, applying
                exponential backoff: 2s, 4s, 8s (max 3 attempts).
  └─ FR-02.5.3  Inosuke SHALL immediately escalate PERMANENT and
                SECURITY_BLOCK failures to Kagaya without retrying, including
                the full step context, failure type, and current state.
  └─ FR-02.5.4  Inosuke SHALL emit a StepCompletionEvent to the IPC Bus
                after every step (success or failure), not only at task end.
